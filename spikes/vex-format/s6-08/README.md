# S6-08: VEX consistency on real decide output (#154)

Do SBOMber's outputs for one real run agree with each other, and does the
pinned consumer act on the VEX it writes? The answer for the current run is in
`results/CONSISTENCY.md`.

```
demo-app/  (lockfile only; never installed or run)
  -> grype 0.112.0 -> build_canonical_scan.py (bridge) -> canonical-scan.json
  -> sbomber usage -> sbomber localise -> sbomber decide
  -> sbomber report (html, text) -> sbomber vex (application and package subject)
  -> consistency.py -> grype --vex (consumer test)
```

`demo-app` covers three decision states across four dependencies: `ini` imported but only
`ini.stringify` called (the vulnerable `parse`/`decode` never are),
`minimist()` and `decode-uri-component` called, `lodash.template` called while
the other lodash advisories name other functions.

## What is real and what is not

- **Bridge:** no command on main writes `canonical-scan.json` from a scan yet
  (Component 1, #121 / #146). `build_canonical_scan.py` builds it from the
  lockfile and a real Grype run; it is the only stand-in. Replace its output
  with Component 1's when that lands, then rerun the identity and consistency checks; finding counts and IDs may change.
- **Real:** Grype, `usage`, `localise` (with provenance and visibility),
  `decide`, `report`, `vex`, and the consumer runs.
- **Not produced:** `findings.json`. #154 names it, but no command writes it.
  The checks cover the HTML and text reports, `decision-results.json` and both
  VEX documents.

## Checks (`consistency.py`)

1. Identity: each finding has one decision, one HTML row, one text entry and
   one statement per supported finding per VEX document, for the same vulnerability and package. Unsupported findings remain in the human reports and are omitted from VEX.
2. State: both reports show the decision's state; statements carry the mapped
   status: guarded positive usage can remain `under_investigation`; reliable positive evidence can map to `affected`; unsupported maps to `omit`. Automated output never asserts `not_affected`.
3. Both VEX documents validate against OpenVEX 0.2.0.
4. No finding is missing from the human report, `unknown` ones included.
5. `contracts/validate.py` passes on the run's contract files.
6. Consumer: Grype with every finding ignored and
   `vex-add: [under_investigation]` re-adds exactly the `under_investigation`
   findings from the package-subject document. The application-subject
   document (R5 rule 1, the team's default since the #128 decision of
   18 October 2026) is reported either way: Grype 0.112.0 does not match it,
   which is the recorded limitation, reproduced here on real output.

CI re-runs `consistency.py --check` on the committed results (offline) and its
tests. Re-run everything with network access:

    export GITHUB_TOKEN=$(gh auth token)
    spikes/vex-format/s6-08/run.sh

## Review hardening and evidence scope

The committed results are the author's 8fced91 rerun after #169 and #170. `CONSISTENCY.md` is regenerated by the corrected checker against those
same saved bytes. This is an offline consistency check, not a new measurement
of the current revision. The real recorded run has no unsupported findings;
a controlled success test checks that an unsupported finding remains in both
human reports while being omitted from VEX.

The checker rejects duplicate decisions, wrong HTML package headings, foreign
VEX subjects, missing scanner identities, changed consumer packages and
unmatched consumer inventories. It checks the pinned binary version, database
identity, source and relevant configuration across the recorded Grype outputs.
A future consumer result is compared by vulnerability AND package, including
multiplicity. An empty application-subject result is a documented consumer
limitation, never evidence that those vulnerabilities do not matter.

`run.sh` now stops if online localisation verification fails. It disables
consumer database auto-update after the initial scan and records the clean Git
revision, binary checksum, demo input hashes and output hashes in
`run-metadata.json`. The checker verifies these hashes on new runs. To replay
without replacing the committed historical evidence:

    SBOMBER_S6_OUT=/absolute/path/to/fresh-results spikes/vex-format/s6-08/run.sh

Issue #154 remains open for the final S6-01 run using Component 1's canonical
writer and the agreed treatment of the missing `findings.json` output. This
PR provides a reviewed harness and demonstration; it does not claim those
integration dependencies are complete.
